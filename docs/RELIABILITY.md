# Исправления надёжности существующего конвейера

Дата проверки: 27 октября 2026. Изменения локальные, без коммита и отправки.

## Семантика admission

1. В PostgreSQL создаётся PUBLISHING с токеном публикации в updated_at.
2. RabbitMQ подтверждает публикацию persistent message.
3. Тот же владелец переводит запись в PENDING; только после этого API возвращает 202.
4. Воркер откладывает PUBLISHING, не увеличивая attempts.
5. Явный отказ или неизвестный результат публикации отменяет admission: REJECTED и 503. Уже опубликованная копия игнорируется потребителем.
6. Reconciliation отменяет PUBLISHING старше PUBLICATION_TIMEOUT_SECONDS. Запоздалый publisher с прежним токеном не может завершить или отменить новую публикацию batch.
7. Batch повторяет ту же строку с тем же task ID; конкурирующий publisher ждёт завершения или отмены текущего admission. Существующая принятая задача не перепубликуется.

Это политика отмены неопределённых admission, без outbox и автоматического replay. При сбое записи отмены в БД процесс reconciliation выполнит её после восстановления БД. Если ответ 202 потерян после commit или БД не подтвердила результат SQL commit, задача может быть выполнена; HTTP idempotency key пока отсутствует. Общий API timeout ограничивает ожидание. Ответ 503 при ошибке БД/общем timeout включает task_id, status_url и Location, чтобы сначала проверять исходную задачу. Это отличается от окончательного отказа при перегрузке. GET при недоступности БД возвращает 503, а не 404/500.

## Владение обработкой

Захват и восстановление выполняются под SELECT FOR UPDATE одной транзакцией. attempts — монотонный fencing token: succeed, fail и heartbeat применимы только к своей текущей попытке в PROCESSING. Payload сообщения сверяется с записью БД; inference использует сохранённый текст.

Heartbeat продлевает lease через updated_at. Повторная доставка не отбирает действующий lease. После гибели процесса восстановление ждёт истечения lease, затем увеличивает attempts. Устаревшая попытка может физически продолжать вычисление, но не может записать результат или изменить состояние новой попытки. По исчерпании попыток сохраняется FAILED.

## Подтверждения и отказы

- SUCCEEDED: ACK после commit.
- FAILED: reject(requeue=False), включая повторную доставку после падения между commit и reject.
- REJECTED: ACK без inference.
- PUBLISHING и активный lease: задержка и nack(requeue=True).
- Недоступность БД: нет ACK; задержка и повторная доставка.
- Неизвестный ID, повреждённый JSON, несовпадающий payload: reject в DLX.

Classic RabbitMQ DLX не даёт абсолютной гарантии доставки в DLQ при потере узла/target. Дубли в DLQ возможны. БД содержит конечное состояние; exactly-once не заявляется. При долгом отказе инфраструктуры повторы продолжаются с ненулевой задержкой, без обещания фиксированного времени восстановления.

## Диагностика и завершение

API /healthz проверяет liveness; /readyz проверяет БД и готовность publisher с общим таймаутом. Healthcheck воркера проверяет модель, RabbitMQ и БД; Content-Length вычисляется по реальному телу. Публикация имеет внешний timeout, включающий ожидание reconnect.

SIGTERM останавливает потребление и ожидает обработчики. Heartbeat отменяется при завершении обработчика; ресурсы закрываются при ошибках старта. Docker stop_grace_period остаётся внешним пределом для зависшего синхронного/native inference: Python не может безопасно прервать произвольный поток.

minio-init завершается ошибкой при неуспешной настройке alias/bucket. Числовые настройки проверяются при старте. Формат текущей таблицы не изменён: используются attempts и updated_at, миграция для этих исправлений не нужна.

## Проверки

- Ruff check и format --check.
- pytest -W error -m "not integration": состояния, fencing, heartbeat, admission expiry, publisher timeout, readiness, ошибки БД и завершение ресурсов.
- pytest -W error -m integration: отдельные Testcontainers PostgreSQL/RabbitMQ; конкуренция транзакций, overflow, DLX, потеря канала после FAILED, HTTP/FastStream/SQL, потерянный confirm и незавершённый admission.
- Отдельные процессы воркера: принудительное завершение во время inference с восстановлением новым процессом; SIGTERM во время inference с сохранением результата.
- Inference в этих испытаниях детерминированно подменён. Они не подтверждают загрузку реальной MLflow-модели и качество классификации.
- Пользовательские сервисы, очереди и тома не изменялись тестами.
